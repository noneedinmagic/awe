# awe — repo audit, 2026-09-27

## 2. Verdict

The engine code is careful: a pure, heavily tested reducer (430 passing tests), fail-closed eligibility, explicit timeouts and retries on every outbound call, and threat reasoning written down next to the code. The weak point is not in the code. It is in the release path. `live` moves to every green `main` and is executed by every consumer's AI orchestration workflow with that consumer's secrets and write token. Yet the `main` ruleset that the split plan called for (require `Tests (node 24)` + `actionlint`, no force-push, no deletion) was created on 2026-09-02 and is **disabled**, and no ruleset covers the `live` tag. The single thing most likely to hurt is a push, whether by a compromised agent credential or a mistaken by-hand `retag-live.sh`, landing on every consumer at once with no human in the loop.

## 3. If I only have two hours

1. **Enable the existing "Default branch checks" ruleset** (≈5 min). It buys required CI plus no force-push or deletion on `main`, which closes the "push straight to main, go green, ship to the fleet" path. The retag job pushes tags only, so enabling it does not affect `live` movement. Then spend up to an hour on the tag half of 2026-09-27-01 (see its first step). That part may need a credential change, so it may not fit.
2. **Add `queue: max` to the `ai-orch-<pr>` concurrency groups** in `.github/workflows/orchestrator.yml` (≈30 min including a dogfood PR). It stops a queued `Report Fix Result` job from being silently cancelled by the next PR event, which strands the PR in `ai:fixing` (2026-09-27-02).
3. **Drop `checks: write` from the `claude-fix` job and log non-2xx Telegram responses** (≈45 min for both). The first removes the fixer's ability to forge the `AI Policy Gate` or required CI check runs (2026-09-27-03, partial). The second makes a permanently rejected notification visible instead of silently retried forever (2026-09-27-04).

### Expanded: Critical and High

**2026-09-27-01: nothing enforces what reaches `live`.** `docs/rollout.md` ("Why `live`") and ADR 0004 (companion repo) make `live` the only supported pin, and it moves automatically. That design is sound only if something guarantees each `live` move is reviewed, green code. Today the guarantee rests entirely on convention.

- **`main`.** The public-split plan (agentic-workflows `docs/research/2026-09-02-awe-public-engine-split.md`, Phase 1 acceptance) ends with "the owner enables branch protection on `main` requiring `Tests (node 24)` + `actionlint`". A ruleset with exactly those rules exists (created 2026-09-02 23:49), but its enforcement is `disabled`, and the effective-rules endpoint returns nothing for `main`. Direct pushes and force-pushes to `main` are therefore accepted. The retag job still requires `test` and `actionlint` to pass on the pushed commit, but no human sees it first.
- **`live` itself.** Tags have no ruleset, so any identity with `contents: write` can re-point `live` with no CI at all. `scripts/retag-live.sh` is explicitly documented as runnable by hand, and the agent App identities have push access to this repo. The next event in each of the consumer repos listed in the companion's split notes then runs that commit's `orchestrate.js` with the consumer's `GITHUB_TOKEN` (write scopes) and, in `claude-fix`, its `CLAUDE_CODE_OAUTH_TOKEN`.
- **Possible reason for the disabled state.** The ruleset may have been created while the repo was still private, and GitHub warns that changing visibility disables some rulesets. No commit, doc or issue here records a deliberate decision to leave it off.

**2026-09-27-02: fix-result displacement.** The `report-fix-result` job was moved into the `ai-orch-<pr>` group on purpose (commit f4e31e5, "round 3 on #1") to serialize its `reduce()` with the `synchronize` run Claude's push triggers. That fixed the race, but it put the job in a group where GitHub keeps only one pending job. Picture a busy moment: a CI `workflow_run`, a review submission, and the fix-result all arrive within the same few seconds. Whichever pending job is not the newest is cancelled. For the orchestrate job this is harmless, because the next run re-derives everything from live GitHub state. For `report-fix-result` it is not, because its `FIX_OUTCOME` input exists only in that job's context. Nothing else reports it. The `|| 'failed'` fallback (orchestrator.yml:277) never runs because the job never starts, and `ai:fixing` is only cleared by a fix-result or a push. Confidence is medium: the mechanism is documented and displacement of the sibling job is routine in production, but a cancelled `Report Fix Result` has not been observed in the runs sampled. `queue: max` is the documented knob. It interacts with agentic-workflows#301, since fewer dropped runs means more concurrent sticky writers only if #301's key change also lands, so settle both in one design pass.

## 5. Latent risks

- **Auto-merge turns 2026-09-27-03 into a merge path.** `merge.auto_merge` is inert today (`scripts/lib/gate.js`, `telegram.js` "merged" hook). The moment it is wired, a forged green gate or forged sticky `ai:ready` becomes a merge rather than a misleading signal. Resolve the fixer-token scoping before implementing auto-merge (`docs/rollout.md:104`).
- **More consumers, more concurrency.** Displacement (02) and the sticky race (05) both scale with events per PR per minute. Busier consumers or a faster reviewer sweep make both likelier without any code change.
- **Going fully public invites fork PRs.** Fork PRs are correctly unmanaged (`isFork`, `scripts/lib/policy.js:387`). `workflow_run` from a fork gets an empty `pull_requests` array and no-ops (`scripts/orchestrate.js:51-53`). Both properties are load-bearing but have no test pinning the `workflow_run`-from-fork case end to end.
- **GraphQL thread comments cap at 100.** `fetchReviewThreads` requests `comments(first: 100)` without paginating inside a thread (`scripts/lib/review-threads.js`, query at ~line 94). `unansweredThreads` reads `.at(-1)` as "latest voice". A thread past 100 comments would be misread. Unreachable today, cheap to guard.
- **Private-ADR references.** A consumer-facing file (`schemas/ai-policy.schema.json`) and 20 other sites cite `docs/adr/000N-*.md` paths that don't exist in this repo (`CONTEXT.md` explains they live in the private companion). If the companion is ever renamed or ADRs renumbered, these become unrecoverable pointers for outside readers.

## 6. What is good

- **Effects are ordered around durability.** Notify, review-request and `should_fix` are resolved *before* the sticky write, with per-latch rollback on failure (`scripts/orchestrate.js:969-1073`). This is the "record around the irreversible act" rule done carefully.
- **The trust boundary is capability-based where it counts.** Policy comes from the default branch, not the PR. The opt-in is attributed to its actual applier through issue events and fails closed when that can't be resolved. Review markers are trusted only from local-sweep logins, and adjudication cards only from reviewer-role authors (`scripts/lib/policy.js:377-408`, `scripts/lib/inspect-review.js:120-128`, `scripts/orchestrate.js:988-994`).
- **Every network call has a timeout and a retry policy chosen per method.** POST is never retried, because it carries no idempotency key (`scripts/lib/github.js:3-7,57-62`). Telegram has its own 10 s abort.
- **The vendored dependency is verified.** CI runs `npm ci` over the committed `node_modules/`, then fails on `git status --porcelain` drift (`.github/workflows/ci.yml:42-49`).
- **`retag-live.sh` refuses to move `live` backwards** (tip-only guard), refuses shallow clones, and pushes the history tag non-forced before the moving tag. Rollback is kept a separate, deliberate act.
- **Tests execute real bodies.** `main()` takes an injected `gh`/`sendTelegram` seam, and 430 tests cover the hotspots directly rather than mocks of them.

## 7. Reusable rules

- **A ruleset that exists but is not enforced counts as absent.** Audit rulesets by the effective-rules endpoint (`/rules/branches/<b>`), never by listing `/rulesets`.
- **A moving release tag that other repos execute gets the same protection as the default branch.** That means restricted update and deletion, with only the release job's credential able to bypass.
- **A job that must not be dropped never shares a concurrency group with high-frequency events, unless the group sets `queue: max`.** `cancel-in-progress: false` does not mean "nothing is cancelled".
- **A token handed to an agent must not hold the identity the system trusts as its own state writer.** If it has to, the state needs an integrity check the agent can't forge.
- **When a doc claims a security property, cite the line of code that enforces it.** Then a code change that strengthens or weakens the property shows up as a stale citation.

## 8. Taste

- Comments reference private-companion issue numbers (`#1`, `#105`, `#119`, "codex review round 4 finding on #1") that mean nothing to a public reader. A `agentic-workflows#N` or `awe#N` qualifier would cost nothing. The bare form is a deliberate carry-over from the import (see `CONTEXT.md`), so this is taste, not a defect.
- The comment-to-code ratio in `orchestrate.js` and `state.js` is very high. The reasoning is valuable, but much of it is incident history better kept in commit messages or ADRs, with the code comment keeping only the invariant.
- `scripts/claude-fix-prompt.md` opens "You are responding to a Codex code review" regardless of which reviewer backend produced the findings.
- `package.json` declares `engines.node >=20`, but the action and CI pin node 24 only. Either test 20 or declare 24.
